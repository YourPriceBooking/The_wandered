Уточнення після аналізу main `f7b6ce1`:
1. API журналу не є звичайним page/limit endpoint: повертає чотири мовні
   колекції, до 4×limit записів, без total. Запит за межами колекції може повернути
   її всю. Adapter запитує page=1/limit=100000, перевіряє унікальність ID та
   насичення ліміту, зберігає повну відповідь і сам визначає межі сторінок.

   бекенду лишається бажаним покращенням етапу 7; поточний контракт перевірений
   на живій відповіді, але не є новим backend API.
2. Замість автоматичного infinite scroll залишено звичайні серверні сторінки:
   початковий HTML, canonical та URL завжди описують одну й ту саму порцію.
   Native anchors дають браузеру керувати історією та відновленням позиції.
   Поведінку в інтерактивному браузері тут не підтверджено: середовище блокує

3. Landing журналу показує три найновіші англійські записи; його page>1

4. Sitemap refresh: 3 паралельні колекції, 4 lookup, загальний бюджет 60 секунд

   Перший холодний запит журналу потребує завантаження повної відповіді API;
   далі використовується кеш. Його оптимізація — разом із backend endpoint в етапі 7.
